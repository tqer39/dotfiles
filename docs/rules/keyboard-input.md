# キー入力・ショートカットのルール

この文書は dotfiles のキー入力設定を調査・変更するときの正本です。
生成されたルールに本文を複製せず、この文書を参照します。

## 目的と操作環境

目的は、次の4環境で共通の操作感を持ち、問題なく使えるキーマップを作ることです。
単一の OS やアプリで動くことだけを完了条件にしません。

| OS・端末 | キーボード | 配列 |
| --- | --- | --- |
| Windows | HHKB Type-S | US |
| Mac Studio（macOS） | HHKB Type-S | US |
| MacBook Pro（macOS） | 内蔵の標準キーボード | US |
| Ubuntu | HHKB Type-S | US |

- 共通仕様は、押す物理キーと実現したい操作で定義します。
  OS ごとの修飾キー名やアプリに送るショートカットは、実装として分けて管理します。
- HHKB のキーと MacBook Pro の元 Caps Lock を同一視しないでください。
  キーの位置・刻印、キーボード本体の設定、OS の設定、実際の入力イベントを区別します。
- 以下の macOS・Karabiner に関する記録は、これまで調査した macOS 環境のものです。
  Mac Studio と MacBook Pro の両方で確認済みとは限りません。
  Windows・Ubuntu の設定やキーイベントにそのまま適用しないでください。
- Windows・Ubuntu のキー割り当て、各 HHKB の設定、各端末のアプリ構成は未確認です。

## 共通の呼称

- **A左キー**は、A キーのすぐ左にある物理キーを指します。
  HHKB では Control、MacBook Pro の内蔵キーボードでは Caps Lock と刻印されたキーです。
- ショートカットは `A左キー+C`、`A左キー+Shift+J` のように表記します。
  この呼称は物理位置を表し、OS に送る Control／Command などの修飾キーとは区別します。
- ユーザーはテキスト操作の修飾キーとして A左キーを使い、Option／Alt は使いません。
  Option／Alt の単語移動を維持する前提で、合意済みの履歴操作を制限しないでください。
- 以前の会話や設定名にある「元 Caps Lock」は、対象機器と物理位置を確認して読み替えます。
  HHKB のキーを Caps Lock と断定したり、すべての Control 入力を A左キーとみなしたりしません。

## 合意済みの共通キーマップ

以下は4環境共通の要求仕様です。設定への反映や実機検証の完了を意味しません。

| 物理キーの組み合わせ | 期待する操作 |
| --- | --- |
| `A左キー+Space` | 入力ソースの切り替え |
| `A左キー+C` | テキストのコピー |
| `A左キー+V` | テキストの貼り付け |
| `A左キー+Tab` | フォーカス中のアプリで次のタブにフォーカス |
| `A左キー+Shift+Tab` | フォーカス中のアプリで前のタブにフォーカス |
| `A左キー+W` | フォーカス中のアプリの現在のタブを閉じる |
| `A左キー+Q` | フォーカス中のアプリを終了する |
| `A左キー+J` | nani.now のクイック翻訳 |
| `A左キー+Shift+J` | VS Code・Cursor などのエディタや Codex で統合ターミナルを開く |
| `A左キー+R` | エディタの統合ターミナルで fzf によるコマンド履歴検索 |
| `A左キー+R`（Codex の内蔵ブラウザ） | 現在のページをリロード |
| `左 Option（左 Alt）+Tab` | アプリの切り替え |
| `Option（Alt）+←` | ブラウザの現在のタブの履歴で前のページに戻る |
| `Option（Alt）+→` | ブラウザの現在のタブの履歴で次のページに進む |
| `右 Option（右 Alt）` の短押し | Superwhisper の音声入力を開始・停止 |

- Tab と Shift+Tab は、アプリの切り替えやタブの並べ替えではなく、タブのフォーカス切り替えです。
  VS Code では既存の合意どおり、端のタブから反対側へ循環させます。
- アプリの切り替えは `左 Option（左 Alt）+Tab` に割り当て、`A左キー+Tab` と区別します。
  Option／Alt は物理キーの左右を区別し、OS に送る修飾キーは実装として別に確認します。
- `A左キー+J` は、どのアプリが前面でも nani.now のクイック翻訳を呼び出す操作です。
  nani.now のウィンドウを開閉する操作には置き換えません。
- `A左キー+Shift+J` はエディタや Codex の統合ターミナル用です。
  VS Code・Cursor はアプリ自身の `keybindings.json` で割り当て、専用の Karabiner 変換は追加しません。
  既存ターミナルを表示してフォーカスし、毎回新しいターミナルを作ったり、終了したりしません。
  Codex は既存のアプリ側のターミナル表示操作への変換を維持します。
  設定の正本と適用方法は [統合ターミナルのショートカット](../terminal-shortcuts.md#エディタの統合ターミナル)を参照します。
- `A左キー+R` は VS Code・Cursor などの統合ターミナルにフォーカスしているときだけ、
  アプリ自身のキーバインドで Control+R をシェルに送ります。
  fzf の履歴検索を利用し、エディタのファイル履歴検索には置き換えません。
  シェルのプロンプトで使い、選択したコマンドは入力欄に戻すだけで自動実行しません。
- Codex の内蔵ブラウザでは `A左キー+R` で現在のページをリロードします。
  macOS は既存の Control-to-Command 変換で `Command+R` を送り、
  Codex 専用の `Command+R` から `Control+R` への変換は追加しません。
  インストール済みアプリのリロード操作の既定値 `CmdOrCtrl+R` を確認しています。
  物理 Command の R 操作と、単独ターミナルアプリの Control+R は維持します。
  Codex の統合ターミナルでの履歴検索との両立と、4環境の実機動作は未確認です。
- `Option（Alt）+←/→` はブラウザの履歴操作です。タブ切り替えや単語単位の移動と区別します。
  左右どちらの Option／Alt も対象とします。Codex は内蔵ブラウザだけでなくアプリ全体に適用します。
  それ以外の対象外アプリのキー操作は変更しません。
  Shift・Command・Control などを追加した組み合わせは、この履歴操作へ変換しません。
  右 Option と矢印の同時押しで、単独短押し用の Superwhisper を起動しないことも確認します。
- `右 Option（右 Alt）` は単独操作で Superwhisper の音声入力を呼び出す要求です。
  短押しで録音を開始し、もう一度短押しで停止するトグル操作とします。
  押している間だけ録音する方式にはしません。
  他のキーとの同時押しで誤起動しないようにし、アプリの対応 OS と実際の設定を確認します。
  各環境での利用可否は未確認であり、未対応の場合も代替アプリを無断で決めません。
- W は現在のタブだけを閉じる操作、Q はアプリ自体を終了する操作として区別します。
  Q は強制的なプロセス終了ではなく、保存確認などを尊重する通常の終了操作として扱います。
  タブがない場合や最後のタブを閉じる場合の扱いは、アプリごとに確認します。
- 入力切り替えは、これまでの要求に基づき入力ソースの切り替えとして扱います。
  IME のオン・オフと同じ動作とは限らないため、各環境の期待動作を確認します。
- ターミナルでもコピー・貼り付けを実現する設計とし、コマンド中断との競合を確認します。
  `A左キー+C` をテキスト未選択時に中断へ切り替えるか、中断を別キーにするかは未確定です。
  コピーという要求だけから、中断操作の削除や未選択時の動作を決めないでください。

## 共通キーマップの設計と完了条件

- 合意済みの共通キーマップを基準に実装します。
  未確定の割り当てや例外動作は、既存設定へ反映する前にユーザーと確認します。
- 対象操作はテキスト編集・タブのフォーカス切り替え・ブラウザの履歴移動・入力ソース切り替え・
  アプリ切り替え・アプリ呼び出し・音声入力・ターミナル操作です。
  共通の期待動作と OS・アプリ固有の例外を整理します。
- コピーとコマンド中断など、同じキーが異なる意味を持つ操作の優先順位を先に決めます。
  アプリの対応状況を確認せず、全環境で同じ変換を適用しないでください。
- OS ごとの設定方法を選ぶ前に、既存設定と競合を確認します。
  Ubuntu のデスクトップ環境・表示セッション、Windows のリマップ方法、
  HHKB 本体の設定など、実装に必要な情報を確認します。
- 同じ操作一覧を4環境で検証し、環境別に成功・失敗・未確認を記録します。
  macOS の自動テスト成功だけで、Windows・Ubuntu や別の Mac の動作を保証しません。

## ブラウザの履歴操作の実装と検証

- macOS は選択中の Karabiner プロファイルで、`Option+←` を `Command+[`、
  `Option+→` を `Command+]` に変換します。対象は Chrome・Brave・Safari・Firefox です。
  ブラウザの入力欄でも同じ変換を適用します。
  Chrome・Brave・Safari の既存ルールを維持し、Firefox を対象に追加しています。
- Codex は、ユーザーが履歴移動を確認した `Command+←/→` に `Option+←/→` を変換します。
  入力欄も含むアプリ全体への適用をユーザーと合意しています。
  A左キー・物理 Command の既存変換は変更せず、Command 側の履歴操作も無効にはしません。
  変換後の Option 操作による実機の履歴移動は、ユーザーによる確認が必要です。
- Windows・Ubuntu はブラウザ標準の Alt+←/→ を利用する方針です。
  [Chrome の公式ショートカット](https://support.google.com/chrome/answer/157179?hl=ja) と
  [Firefox の公式ショートカット](https://support.mozilla.org/en-US/kb/keyboard-shortcuts-perform-firefox-tasks-quickly)
  を根拠とし、OS 側の競合を確認せずに追加のリマップを導入しません。
  macOS の `Command+[` と `Command+]` はこれらと
  [Safari の公式ショートカット](https://support.apple.com/ja-jp/guide/safari/cpsh003/mac) も参照します。
- macOS の変換・対象外アプリ・追加修飾キーは `tests/test-karabiner.py` で検証します。
  4環境の実機動作は未確認です。履歴のあるタブで戻る／進むを確認し、入力欄へのフォーカス時と
  右 Option の音声入力との競合も検証してください。
- リポジトリの設定とホームの Karabiner 設定が別ファイルの場合、自動では反映されません。
  適用時は既存設定の差分を確認し、他のキー設定を上書きしないでください。

## macOS の物理キーと変換後のキーを区別する

- 「元 Caps Lock」は物理的な Caps Lock キーを指します。
  ユーザーの macOS システム設定では Command に割り当てられています。
  この設定を前提にし、Control への変更をユーザーに求めないでください。
- 物理キー、macOS の修飾キー設定、Karabiner の入力イベント、変換後の出力、
  アプリ側のショートカットを分けて確認してください。
- この環境では元 Caps Lock が Karabiner EventViewer 上で `left_control` と
  表示された実績があります。現在の設定は左右の Control を扱っていますが、
  すべてのキーボードで同じイベントになるとは断定しないでください。
- 通常のテキスト操作では A左キー+A/C/V を Command+A/C/V として扱います。
  物理 Command の既存ショートカットも維持してください。

## macOS の例外ルールの考え方

- `src/.config/karabiner/karabiner.json` の選択中プロファイルとルール順を確認します。
  実際に読み込まれるユーザー設定との一致も、リンク先と内容で確認してください。
- 汎用の Control-to-Command 変換は `original_control_pressed` を設定します。
  変換後の Command に対する例外では、この変数で物理 Command と区別してください。
  この変数は Control 入力で設定されるため、物理 Caps Lock 専用の識別子ではありません。
- ターミナルでは Control を使う既存操作を考慮し、汎用変換とは別に検証します。
  変換されない経路に、変換時だけ設定される変数を必須条件として追加しないでください。
- タブ操作の「移動」はタブの並べ替えと区別します。
  VS Code ではフォーカスを次・前へ切り替え、端から反対側へ循環させる意図です。
- Codex の `A左キー+Shift+J` はターミナルを開く操作です。
  `A左キー+J` の例外と衝突させないでください。

## macOS の Nani の操作を区別する

- ユーザーの意図は、どのアプリが前面でも `A左キー+J` で nani.now のクイック翻訳を呼び出せることです。
  アプリを開く操作と、選択したテキストのクイック翻訳は区別し、後者を実装対象とします。
- 変更前に Nani の設定画面と保存設定を確認し、要求された操作の割り当てを選びます。
  スクリーンショットの修飾キー記号を省略して読み取らないでください。
- 2026-10-04 に確認した保存設定では、クイック翻訳は `Control+Option+J` です。
  保存値は `Control`, `Alt`, `KeyJ` で、`Alt` は Option を意味します。
  同日の設定画面では「アプリを開く」は `Command+Control+J` と表示されています。
  これらは環境固有の確認値であり、変更時に再確認してください。
- 前回の `Control+J` という説明は Option を読み落とした誤りです。
  現在の実装やテストがその値を期待していても、正しい仕様の証拠にはしないでください。

## 調査と検証

- まずアプリ側の直接ショートカットと、A左キーからの変換経路を切り分けます。
  物理 Control 自体も変換され得るため、押したキーだけで出力を断定しないでください。
- macOS では Secure Keyboard Entry を原因と断定する前に、入力イベントとアプリ側の受信を確認します。
- Karabiner の意味のある変換変更では `tests/test-karabiner.py` を更新し、`mise run lint` を実行します。
  テストは仕様から期待値を決め、実装値を書き写すだけにしないでください。
- 自動テストと実機確認を区別します。前面アプリ、テキスト選択の有無、物理キー、
  観測した出力、Nani の表示結果を記録し、実機未確認なら明記してください。
